# 01. 序言与纯 Go 桌面开发哲学

欢迎来到 Antigravities 开发实战！在开始编写第一行代码之前，我们先来探讨一个对于 Go 初学者非常关键的问题：**为什么我们要用纯 Go 开发桌面应用？我们该如何跨越技术选型的陷阱？**

---

## 1. 为什么不用 Electron 或 Tauri？

过去开发桌面客户端，大多数人首先想到的是：
- **Electron**：Chromium + Node.js。优点是 Web 生态丰富，但缺点是打包体积大（动辄 100MB+），启动慢，且空闲内存占用常年维持在数百兆。
- **Tauri**：Rust 后台 + 系统 WebView。相比 Electron 已经轻量很多，但开发需要同时掌握 Rust 语法、Node 打包流水线（Vite、Rollup 等），构建时还要依赖大量 C 库。

而在 Go 语言生态中，我们有了 **MyGo** (`github.com/egoist/mygo`)：
- **零 Cgo（Zero-Cgo）**：纯 Go 代码，不需要在机器上配置 GCC / Clang / MinGW。
- **直接绘制的原生声明式 UI (`mygo/ui`)**：使用纯 Go 构建界面，完全摆脱了 Node.js、Bun、Webpack、Vite 等繁重的 Web 前端工具链。
- **极致的启动速度与内存**：启动只需几十毫秒，空闲常驻内存低至 20MB。
- **单二进制交付**：最终编译产物就是一个干净、独立的 Go 可执行文件，双击即运行。

---

## 2. 深入理解：什么是 CGO？为什么要坚决禁用它（`CGO_ENABLED=0`）？

在 Go 语言的学习与进阶过程中，你一定会频繁听到两个词：**CGO** 和 **Zero-Cgo**。这是初学者跨向工业级 Go 开发的关键一步。

### 2.1 什么是 CGO？

**CGO 是 Go 官方提供的一套互操作机制（FFI），允许 Go 代码与 C 语言代码互相调用。**

在 Go 代码中，只要写了如下片段，Go 编译器就会自动开启 CGO 特性：

```go
package main

/*
#include <stdio.h>
void sayHello() {
    printf("Hello from C!\n");
}
*/
import "C" // 特殊的虚拟包导入，触发 CGO

func main() {
    C.sayHello() // Go 代码直接调用 C 函数
}
```

#### CGO 诞生的历史背景
Go 语言发布于 2009 年。在当时，Go 的生态刚刚起步，而 C/C++ 已经统治系统编程数十年，拥有极为庞大成熟的资产（例如 SQLite 数据库、OpenSSL 加密库、图形图像处理库等）。为了让 Go 开发者不需要从零重写这些轮子，官方推出了 CGO，让 Go 能够“借鸡生蛋”，直接复用海量的 C 语言开源库。

比如著名的 SQLite 驱动 `github.com/mattn/go-sqlite3`，底层就是直接用 CGO 包裹了 SQLite 的 C 语言源码。

---

### 2.2 为什么说 CGO 是一把双刃剑？（初学者的四大痛点）

Go 语言核心贡献者 Dave Cheney 曾写过一篇影响深远的技术博客：*《cgo is not Go》*。在现代 Go 开发中，盲目引入 CGO 会带来以下严重隐患：

1. **丧失 Go 标志性的“秒级闪电编译”**：
   - 纯 Go 项目的编译速度极快（通常只需 1~2 秒）；
   - 一旦开启 CGO，Go 就必须将代码转交给系统安装的外部 C 编译器（GCC 或 Clang）。对于大型 C 依赖，编译时间会飙升数倍甚至数十倍。
2. **跨平台交叉编译陷入“噩梦模式”**：
   - 在纯 Go 下，你只需在 macOS 上敲一行 `GOOS=windows GOARCH=amd64 go build`，即可立刻生成 Windows 程序的 `.exe` 文件；
   - 一旦开启 CGO，上面的命令会直接报错！因为你需要提前在 Mac 上配置好一套面向 Windows 的专用 C 交叉编译器工具链（如 `mingw-w64`），还要处理极其繁琐的 C 头文件路径和链接参数，初学者极易崩溃。
3. **Goroutine 轻量调度与栈切换惩罚**：
   - Go 的协程栈（Goroutine Stack）是动态伸缩的（起始仅 2KB）；
   - 而 C 语言函数假定运行在固定大小的大线程栈上（通常 1MB~8MB）。每次从 Go 调进 C，Go 运行时必须切换线程上下文、调整栈帧并通知调度器避让，带来显著的执行开销。
4. **系统动态链接与“glibc 版本地狱”**：
   - 使用 CGO 编译的程序，默认会动态链接运行机器上的系统 C 库（如 Linux 的 `glibc`）；
   - 一旦生产环境或用户电脑的 `glibc` 版本比你的开发机低，程序双击就会直接崩溃报 `version 'GLIBC_2.34' not found`。

---

### 2.3 什么是 `CGO_ENABLED=0`？

设置环境变量 `CGO_ENABLED=0`，是向 Go 编译器下达最高指令：

> **“彻底禁用 C 编译器，只使用 Go 原生工具链进行构建，严禁任何 `import "C"` 代码通过编译。”**

它的好处显而易见：
- **生成纯正的静态二进制文件（Static Binary）**：不依赖任何宿主机 C 动态库，拷到哪台同架构机器上都能直接运行。
- **交叉编译畅通无阻**：无需任何第三方工具链，随时为 Windows/Linux 编译二进制。
- **纯粹的 Go 调试体验**：无需处理 C 语言的段错误（Segmentation Fault）与内存泄漏调试。

---

### 2.4 禁用 CGO 后，Antigravities 如何做系统调用和数据库？

你可能会问：既然关掉了 CGO，那我们怎么操作 SQLite 数据库？又怎么调用 macOS 的底层窗口？

答案是：**现代纯 Go 方案（Pure Go Alternatives）**。

1. **数据库**：我们选用 `modernc.org/sqlite`。该库通过机器自动翻译技术将 SQLite 的官方 C 源码完整转换为了纯 Go 代码，拥有 100% 的 SQLite 功能与 SQL 语法兼容，但完全没有一行 C 代码，天生支持 `CGO_ENABLED=0`！
2. **底层操作系统调用**：我们使用由 Go 团队成员研发的 `purego` 库。它通过 Go 汇编指令直接在运行时与操作系统动态库进行系统调用，绕过了 C 编译器阶段，让我们可以直接在 macOS 上调用 AppKit 毛玻璃窗口与系统托盘，纯粹又优雅。

## 3. 核心架构设计思想

Antigravities 作为一个专为 Antigravity 开发者设计的账号切换与配额监控工具，其核心设计遵循以下原则：

1. **宁缺毋滥的依赖管理**：
   - 拒绝引入带 Cgo 的包。
   - 数据库操作使用纯 Go 编写的 `modernc.org/sqlite`。
   - 底层系统调用通过纯 Go 的 `purego`（macOS/Linux）或标准库 `syscall`（Windows）。
2. **安全第一的显式控制**：
   - 后台默默刷新配额，但**账号切换绝不静默发生**，必须由用户在托盘显式点击。
   - 对任何外部 SQLite 数据库（如 VS Code 的 `state.vscdb`）的修改，前置必须自动生成 `.bak` 备份文件。
3. **主线程与并发纪律**：
   - 网络 I/O（OAuth 授权、配额请求）全部放在独立 Goroutine 中异步运行。
   - 所有 UI 组件的修改和状态变更，强制排队回主线程 (`app.OnMain(...)`) 执行，杜绝界面渲染崩溃。

## 4. 你的专属实战路径：每一行代码由你亲手书写

本教程的所有章节均按照**小颗粒度、渐进式切片**来组织。在接下来的旅程中：

- **你不必依赖任何预设好的完整代码包**：你将从一个完全空白的目录开始；
- **每一步都由你亲手键入**：从建立 `main.go`、初始化结构体，到写下第一行 `http.ListenAndServe` 和 SQLite 事务；
- **每一步都有即时测试命令**：不需要写完全部代码才能运行，每完成一小节，你都能运行针对该切片的单元测试，确保你的代码完全正确。
